# Parallel BFS on GPU with Overlapped Computation and Data Transfer

This project implements and compares three CUDA versions of parallel BFS on a k-NN graph, where the graph itself lives in host (CPU) RAM instead of GPU memory. The goal is to see how much overlapping data transfer with computation actually helps once the graph is too big to just dump on the GPU.

## Problem Statement

BFS is a natural fit for GPU parallelism, but in practice the graph is often too large to fit entirely in device memory. So the graph stays in host RAM and the GPU has to keep pulling neighbour data from the CPU as it discovers new nodes. That data transfer can easily become the bottleneck if it's not handled carefully.

The assignment asks for three versions of the same BFS, each improving on the transfer bottleneck:

- **Task 1 - Baseline:** A level-synchronous parallel BFS where the GPU asks for the neighbours of the current frontier and the CPU copies them over synchronously. The GPU sits idle while this copy happens.
- **Task 2 - Streams:** Same BFS, but the host-to-device and device-to-host transfers are overlapped with kernel execution using multiple CUDA streams, so the GPU isn't just waiting around for data.
- **Task 3 - CUDA Graphs:** Takes the streamed version further by capturing the whole per-level sequence of kernel launches and memory copies as a CUDA Graph and replaying it, cutting down on launch overhead.

All three versions must produce identical BFS results (same discovery order per level), and the whole point is comparing their runtimes across graph sizes to see how much overlap and reduced launch overhead actually buy you.

The graph itself is a k-NN graph built from the SIFT1M dataset (128-dimensional vectors), with a fixed out-degree per node. `build_knn_graph.py` generates these graphs and also picks a starting node for the traversal.

## Build Instructions

The `.cu` files are picked up from whatever directory `build.sh` is run in, so run it from inside `Implementation/`:

```bash
cd Implementation
chmod +x ../Script/build.sh
../Script/build.sh
```

This will:
- Compile all three CUDA files into `bfs_baseline`, `bfs_stream`, `bfs_graph`
- Generate a wrapper script `bfs.sh` that runs all three tasks one after another
- Create a symlink `bfs -> bfs.sh` for convenience

All of this happens inside `Implementation/`, so that's where the binaries and `bfs` link end up.

## Run Instructions

```bash
./bfs <absolute_path_to_graph.csv> <absolute_path_to_sift_base.fvecs> <start_node>
```

Running `./bfs` executes all three tasks back to back and produces three output files:
`output_<graph_name>_task_1.txt`, `output_<graph_name>_task_2.txt`, `output_<graph_name>_task_3.txt`.

The `Output/` folder in this repo only has results for `graph_100k_64.csv`, but the report covers runs on several other graph sizes too.

## Output Format

Each output file lists, level by level, how many nodes were discovered and which node was closest/farthest from the start node at that level:

```
<level>,<nodes discovered>,<farthest node>,<farthest dist>,<closest node>,<closest dist>
```

Level 0 is always the start node itself (distance 0). The last line of the file reports the total BFS time in milliseconds. 


## Notes

- All three implementations were checked to produce the exact same traversal (level, node counts, closest/farthest nodes) - only the runtime differs.
- The wrapper script exists just so all three tasks can be run and compared with a single command instead of invoking each binary separately.

**Dataset:** 128-dimensional SIFT vectors from `sift_base.fvecs` (ANN_SIFT1M)

**Graph sizes tested:**
- graph_100_8.csv
- graph_5k_128.csv
- graph_50k_64.csv

- graph_250k_64.csv
